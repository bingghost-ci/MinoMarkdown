# Mino 性能与精简方案

版本：v0.1 · 日期：2026-11-12 · 任务：T91–T104 · 状态见[开发进度](06-开发进度.md)。

2026-11-12 用户要求：“review 所有的代码，务必确保程序是高效的，性能强的，代码要精炼，不要出现冗余，一切都保障程序运行流畅不要出现卡顿”，并要求先写出技术方案，“保障每个改进都切实有效”，再据此拆开发计划。本文是那次审查的结论和改法；任务拆分在[开发计划](03-开发计划.md)的 T91–T104，执行入口是[Goal 列表](04-Goal命令列表.md)的 G91–G104，验收在[验收与发布 §8I](05-验收与发布.md)。

## 1. 审查范围与结论

审查覆盖 `src/` 与 `src-tauri/src/` 的全部源码（约 1 MB）、构建配置和打包产物，基于提交 `0f53d30`。下文的行号都是该提交时的位置，实施前以实际代码为准。

**数字的来历：** 打包体积是实际构建量出来的；其余耗时是读代码得出的估计，没有在应用里做过性能剖析。因此每项改动都要按 §2 先量后改，不能凭本文的估计就算完成。

卡顿和臃肿集中在四处：

1. **主线程上重复的全文解析。** 分析已经搬进 worker，但保存、写草稿、打开文件时主线程又用同一个解析器把全文再解析一到三遍。
2. **任何状态变化都重渲染整个应用。** `App.tsx` 把主 hook 的整个返回对象传给每个组件，`src/app` 里没有一个 `memo`；AI 流式输出、输入法组词、字数刷新都会触发。
3. **入口包 3,122 kB，约 75% 不必在启动时加载。** 窗口要等入口包执行完才显示。
4. **Rust 侧的重复劳动。** 每次写设置都重建原生菜单；SHA-256 走软件实现；同一份文件被重复读取、哈希、解码。

另有一处不属于性能的问题：保存时留下的备份文件从不清理（§3.11）。

已经做对、不需要再动的部分列在 §6，避免重复排查。

## 2. 保证每项改进有效的办法

每一项改动都按下面六步做，缺一步不算完成。

1. **复核。** 打开本文指的代码，确认问题仍然存在。代码已经变了、问题不存在的，在证据文件里写“不适用”和原因，跳过。
2. **改前测量。** 用该项“验证”一栏指定的办法取得改前数值，写入证据文件。T91 统一取一次全量基线。
3. **改动。** 只做该项描述的改动。顺手发现的其他问题记到证据文件，不在本项里改。
4. **改后测量。** 同一办法、同一输入再量一次。
5. **判定。** 达到“验证”一栏的门槛才保留。没有达到的，撤回这项改动，在证据文件写“无效，已撤回”和两次数值，不为了保留改动而调整门槛。
6. **行为不变。** `npm run typecheck`、`npm run test` 通过；涉及 Rust 的加 `cargo test --lib --manifest-path src-tauri/Cargo.toml`。改动触及的行为要有测试覆盖，没有的先补测试再改。

### 2.1 三类验证办法

| 类别 | 办法 | 用在哪里 |
| --- | --- | --- |
| 结构性（首选） | 测试里统计调用次数或渲染次数；构建时检查入口包不含某模块、不超过体积预算。结果确定，不受机器负载影响，并且留在仓库里防止以后退化 | 重复解析、重渲染、入口包、菜单重建 |
| 同口径计时 | `scripts/perf-baseline.mjs`（Node）和 Rust 里 `#[ignore]` 的计时测试，取 5 次中位数。只用于改前改后对比，不代表 WebKit 里的绝对耗时 | 查找、哈希、解码、序列化 |
| 实机观察 | 在打包后的应用里操作，用 Web Inspector 时间线或体感 | 滚动、缩放、输入法、启动 |

代理做不了实机观察。凡是只能实机确认的，状态记 `PENDING`，不写成通过。

### 2.2 留在仓库里的守护

这些检查在 T91 和各任务里加入，之后的改动一旦退化就会失败：

- **入口包预算。** `vite.config.ts` 增加一个构建插件：入口包超过预算、或含有 `@codemirror/`、`prosemirror-`、`katex`、`mermaid`、`pdfjs-dist` 的模块时构建失败。预算在 T98 完成后按实测值加 10% 定下。
- **主线程解析计数。** Vitest 用例断言：可视模式保存、无恢复图片的草稿写入，`imageUrlsIn` 的同步解析次数为 0。
- **渲染计数。** Vitest 用例断言：AI 流式片段到达时，文件树、大纲、标签栏不重渲染。
- **菜单重建。** Rust 测试断言：语言没变的设置补丁不触发菜单更新。

### 2.3 红线

以下各项在任何一项改动里都不能削弱，冲突时放弃该项优化：

- 路径授权与每次请求的复查、符号链接拒绝；
- 按磁盘哈希的冲突检测、原子保存的落盘顺序（fsync → 复查 → 链接 → 改名 → 目录同步）；
- 保存的字节保真（front matter、BOM、换行、末尾换行）和文本编码的无损规则；
- HTML 净化、导出与预览不加载远程图片；
- 中文输入法组词期间的保护；
- webview 的 CSP 与权限不放宽，网络请求只在 `ai.rs`；PDF 渲染不用 `fetch`、不开 WebAssembly；
- 代码注释里标了任务号的既有修复（如 T69、T77）不撤回。

### 3.11 保存备份的清理（T101）

`atomic_write.rs:206-216`：每次带 `expected` 的提交都把旧文件硬链接成 `.mino-backup-<文件名>-<哈希前16位>.bak`，没有任何代码删除它。2026-11-12 本机的应用数据目录里已有 296 个（`settings.json` 198 个、`recent.json` 77 个）。用户文档走同一条路径，每次保存内容有变都会在文档旁边留下一份隐藏的旧副本。

改法：

- 目录同步成功之后，按确切的前缀 `.mino-backup-<文件名>-` 列出该文件的备份，按修改时间保留最新的 N 份，其余用 `unlinkat` 在已持有的目录句柄上删除。清理失败不影响保存结果。
- N 的默认值：用户文档 3 份，应用自己的记录文件（设置、最近文件、阅读位置、AI 配置）1 份。2026-11-12 用户决定一律只保留最新 1 份，实现以此为准。
- 落盘顺序不变，“保存后可恢复上一版本”（[技术设计 §7.2](02-技术设计.md)）在 N ≥ 1 时仍成立。

验证：Rust 测试覆盖“连续保存 5 次后只剩 N 份且是最新的”“不删除前缀相近的其他文件”“清理失败时保存仍成功”。

这一项会删除用户文档目录里由本应用创建的隐藏文件。N 的取值是产品决定，见 §5。

## 6. 已核对、无需改动的部分

- **按键路径：** `updateSession` 只推进 ref 和三个防抖定时器；编辑器监听的是 `updated` 而不是 `markdownUpdated`，按键不触发序列化；工具栏状态经 JSON 去重。
- **草稿与自动保存：** 防抖 1.5 秒、最长 10 秒，输入法组词期间推迟，已存的图片不重复上传。
- **滚动与拖拽：** 一个捕获阶段的监听，进度条在 `requestAnimationFrame` 里只改 `transform`；面板拖拽直接写样式、松手才提交。
- **风格切换：** 只改 `data-theme` 和 CSS 变量，样式表只安装一次。
- **Rust 命令：** 所有读写磁盘、哈希、解码的命令都不在主线程；`DocumentStore`、`WorkspaceStore` 的锁不跨文件读写持有；`mino-asset` 协议是异步的。
- **二进制传输：** 图片经 `stage_binary` 以原始字节传递，不走 JSON 数组；`read_document_range` 返回原始响应。
- **AI 流式（Rust 侧）：** 已按 30 ms 合并片段，缓冲区有界，取消在 20 ms 内返回；钥匙串每次请求只读一次。
- **代码拆分：** 编辑器、PDF、源码编辑器、Mermaid、KaTeX 导出字体、语言语法都是按需加载；思源宋体与黑体已按区间切片。
- **有界的存储：** 暂存区、快照、阅读位置都有数量或时间上限；编辑器池上限 5 个。
- **列表规模：** 文件树每个目录分页 200 条，搜索结果上限 500，差异上限 2000 行，不需要虚拟滚动。
