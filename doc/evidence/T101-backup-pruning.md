# T101 保存备份的清理

状态：automatedVerified（计划层级 nativeVerified，实机 PENDING）。2026-11-12。

## 改前

`atomic_write` 每次替换已有文件都把旧版本硬链接为 `.mino-backup-<文件名>-<哈希前 16 位>.bak`，没有任何代码删除它。2026-11-12 本机的应用数据目录 `~/Library/Application Support/app.mino.markdown` 里有 296 个这样的文件。用户文档每次保存内容有变，也会在旁边多一份隐藏的旧副本。

## 改后

提交成功、目录项同步完成、目录位置复核通过之后，调用 `prune_backups`：

- **保留份数：** 用户文档（`commit`）3 份，应用自己的记录文件（`commit_canonical_parent`：设置、最近文件、阅读位置、AI 配置）1 份。按方案 §5 的默认值。
- **候选范围：** 只有名字恰好是 `.mino-backup-<文件名>-<16 位十六进制>.bak` 的普通文件。前缀相近的其他文件的备份、位数不对或含非十六进制字符的名字、同名的目录和符号链接都不在范围内。判断用 `fstatat(AT_SYMLINK_NOFOLLOW)`，不打开、不跟随任何东西；删除用 `unlinkat`，作用在保存时一直持有的目录句柄上。
- **次序：** 按备份的状态变更时间（建立硬链接的时刻，即该版本被替换的时刻）排序，删最旧的。
- **刚被替换的那一版始终保留**，即使它的备份文件是很久以前建立的（内容与某个旧版本相同时会复用已有的备份）。
- **失败不影响保存：** 清理在返回成功之前的最后一步，任何一步出错都直接跳过。

落盘顺序（写临时文件 → fsync → 复查磁盘版本 → 建备份链接 → 改名 → 目录同步 → 复核目录位置）没有改动，原有的故障注入测试全部通过。

此前累积的旧备份会在各文件下一次被写入时清理：应用数据目录里的 296 个，会在设置、最近文件、阅读位置、AI 配置各自下一次保存后降到每个文件 1 个；用户文档旁边的旧备份在该文档下一次保存后降到 3 个。**这一步会删除用户文档目录里由本应用创建的隐藏文件，属于方案 §5 里按默认值执行的事项。**

非 macOS 的回退分支没有加清理：它不会编译进发布的应用，是否保留这些分支见方案 §5。

## 测试

Rust 新增 3 项（`atomic_write` 共 10 项通过；全部 Rust 测试 140 项通过、4 项忽略）：

- `a_document_keeps_its_three_latest_earlier_versions`：连续保存 6 次（v0 → v6），每次保存后都能读回刚被替换的版本；结束时目录里只有文档和 v3、v4、v5 三个备份，没有残留的临时文件。
- `a_record_the_app_keeps_for_itself_keeps_one_earlier_version`：先放入 40 个旧版应用留下的备份，再按 one → two → three → two → three 保存；结束时只剩最后被替换的那一版（two）的备份，40 个旧备份全部清除。
- `pruning_touches_only_this_files_own_backups_and_never_fails_the_save`：目录里预先放入 5 个名字相近但不属于该文件的文件、1 个与备份同名的目录、1 个与备份同名并指向目录外文件的符号链接；保存 6 次后这些全部原样保留，链接指向的文件未被改动，属于该文件的备份仍是 3 个，保存全部成功。

“清理失败时保存仍成功”没有用故障注入直接测：`prune_backups` 没有返回值，调用点在成功返回之前，这一点靠代码结构保证；测试覆盖的是不可删除的对象（目录、链接）被跳过的情况。
