# Mino 验收清单

版本：1.0.0 · 日期：2026-11-20

自动化测试覆盖逻辑；Finder、中文输入法、系统 PDF 与打印、拖放、窗口和性能只能在 Mac 上用手验证。本文是这份实机验收的清单，以及发布一个版本的步骤。功能说明见 [产品说明](01-产品说明.md)，实现见 [技术设计](02-技术设计.md)，各项当前状态只记在 [开发进度](04-开发进度.md)。

## 1. 怎么算通过

| 层级 | 证明了什么 | 不能代替 |
| --- | --- | --- |
| 自动化 | 类型、单元测试、故障注入、构建检查通过 | 系统输入法、剪贴板、Finder、打印面板 |
| 已构建 | 确定版本的 arm64 包能生成，ZIP 与 manifest 一致 | 安装后的运行、签名与公证 |
| 实机验证 | 在记录的 macOS 和机器上按本清单操作，结果与预期一致 | 其他系统版本、其他机器、使用者本人的结论 |
| 用户验收 | 使用者对明确的版本和范围给出结论 | 之后的版本 |

- 用了模拟、注入或合成数据的结果要写明。注入的磁盘满与真实磁盘满分开记，浏览器里的中文输入与系统输入法分开记，“打印面板弹出”与“PDF 文件已生成”分开记。
- 伪造 IPC 令牌、控制回调先后、注入磁盘满属于开发者负例，由自动化测试留证，不要求在界面上手工制造；但它不能代替同一项的实机操作。
- 改动影响到的项要用新构建重测；与改动无关且已通过的项不必重复。

**严重性**

- 阻断发布：正文丢失、静默删除未知语法、已有图片失效、越权访问文件、文档里的脚本被执行、中文输入不可用、必需的导出失败、已检测到外部修改仍直接覆盖、取消或失败被报告为成功。
- 一般问题：视觉瑕疵、文案、不影响数据的交互问题。照常记录，不与上一类混在一起。
- 一项失败时保留操作前后的文件与哈希、截图和准确的错误文字，查明原因后修复，再用新构建重测该项。

## 2. 自动化检查

每次实机验收之前在仓库根目录运行，全部以退出码 0 结束、没有失败用例才开始手工部分。

```sh
npm ci --no-audit --no-fund                              # 按锁文件安装
npm run archcheck                                        # Node、Rust、Tauri CLI 都是 arm64
npm run typecheck                                        # tsc --noEmit 无错误
npm run test                                             # Vitest 全部通过
cargo test --lib --manifest-path src-tauri/Cargo.toml    # Rust 测试全部通过
npm run build                                            # 构建成功
node scripts/generate-font-table.mjs --check             # 字体表与字体包一致
node scripts/generate-paper-textures.mjs --check         # 纸张纹理与脚本一致
python3 scripts/generate-format-fixtures.py --check      # 格式样例与脚本一致
python3 scripts/generate-license-text-bundle.py --verify # 第三方许可文本合集与索引一致
./build.sh                                               # 干净的 release 包、ZIP 和 manifest
node scripts/package-manifest.mjs verify                 # 包与 manifest 一致（build.sh 结尾已运行一次）
```

- `npm run build` 自带三项守护：入口包不含编辑器、CodeMirror、PDF.js、Mermaid、KaTeX 且不超过 `ENTRY_BUDGET_BYTES`；随包字体不超过 `FONT_BUDGET_BYTES`；worker 产物不含依赖 DOM 的模块。任一项不满足时构建失败。
- `./build.sh` 另外检查主程序是 arm64、包内没有 dSYM、`dist` 里没有 source map。
- `manifest verify` 核对 ZIP 完整、ZIP 与 `.app` 的文件清单和内容一致、架构为 arm64、最低系统声明为 12.0、版本与 `src-tauri/tauri.conf.json` 相同。它只证明本地打包完整。

## 3. 准备

**应用。** 两种方式，按要测的内容选：

- `./build.sh` 后直接打开 `src-tauri/target/release/bundle/macos/Mino.app`。性能测量和需要包哈希的记录用这种，构建产物都留着。
- `./install.sh`：构建、装到 `/Applications`、刷新 Launch Services、打开应用，最后运行 `./clean.sh` 删除 `src-tauri/target` 和 `dist-package`。Finder“打开方式”和 Dock 拖入用这种。它会请正在运行的 Mino 退出。
- `./start.sh` 是开发模式，不用于验收。

**记下环境。** macOS 版本、机型、输入法及版本、应用版本、主程序 SHA-256、开始时间：

```sh
sw_vers
shasum -a 256 src-tauri/target/release/bundle/macos/Mino.app/Contents/MacOS/mino-markdown
```

**样本。** 只改副本，不改仓库里的样本，也不用自己的真实文档做破坏性操作。

```sh
sample_root="$(mktemp -d "${TMPDIR:-/tmp/}mino-acceptance.XXXXXX")"
ditto tests/fixtures/markdown "$sample_root/markdown"
ditto tests/fixtures/formats "$sample_root/formats"
python3 -c 'from pathlib import Path; import sys; Path(sys.argv[1]).write_bytes((b"a" * 1023 + b"\n") * 11264)' "$sample_root/markdown/large-source-11MiB.md"
printf '样本副本：%s\n' "$sample_root"
```

| 位置 | 内容 |
| --- | --- |
| `tests/fixtures/markdown/` | F01 基础、F02 列表、F03 代码与长代码、F04 链接与路径（含 `assets/` 里文件名带中文、空格、`#%()` 的图片）、F05 表格与长表、F07 草稿、F08 front matter 与未知语法、F09 BOM、CRLF、空文件、无效 UTF-8、F11 恶意内容、F12、F13 |
| `tests/fixtures/formats/` | GB18030、UTF-16、Big5、UTF-8 文本，JSON、YAML、日志、CSV、TSV、HTML，`sample.pdf`、`scanned.pdf`，以及伪装成文本和 PDF 的文件；由 `scripts/generate-format-fixtures.py` 生成 |
| `tests/fixtures/manifest.json` 等 | 各样本的哈希、期望和用途 |
| `dist-package/performance-fixtures/` | 规模样本，需要时生成（见下） |

规模样本（100 KiB、1 MiB / 1 万行、5 MiB 文档，1 万条目的目录，20 张合成图片）：

```sh
node scripts/generate-scale-fixtures.mjs dist-package/performance-fixtures   # 目标须是空目录
```

生成 10,023 个文件，其 manifest 的哈希锁定在 `tests/fixtures/F10-scale.json`。`./clean.sh` 会连同 `dist-package` 一起删掉它们。

另外准备自己的真实文件，不放进仓库：真实的系统截图，GBK 小说，带书签的 PDF、扫描版 PDF、加密 PDF、百页以上和 50 MiB 以上的 PDF，5 MiB 以上的 TXT，带图的长文档，多表格文档。还需要一个外部编辑器（制造冲突）、一个独立浏览器（看导出的 HTML）和断网的办法。

## 4. 实机验收清单

行末括号是来源：A、B 为原始验收编号，T 为任务编号。“保存重开”指保存、关闭标签、再打开同一文件。

### 4.1 打开与保存

- [ ] 冷启动后是一篇空白的“未命名”文档，可直接输入；`⌘S` 弹出存储面板，保存后标题和状态更新。
- [ ] `⌘O` 打开 F01 单个文件，不先开文件夹：以阅读模式显示，`⌘⇧R` 进入可视化编辑。(A02)
- [ ] 在 Finder 里双击和用“打开方式”打开，应用未运行与已运行各一次：都进入同一套文档流程，已有未保存内容不丢。(B08)
- [ ] Finder“打开方式”里，Markdown、TXT、源码文件和 PDF 都列出 Mino，且 Mino 没有成为它们的默认应用。(T81)
- [ ] 把文件、文件夹拖进窗口：文件以阅读模式打开，文件夹出现在文件栏。(B08)
- [ ] 把 `.md`、`.txt`、源码、PDF、文件夹拖到 Dock 图标上分别打开；Word、图片、压缩包不被接受。(T109)
- [ ] 文件菜单“打开最近使用”：打开文件后列表更新；选一个已被删除的项，给出提示而不是空白或崩溃。(B08)
- [ ] 打开对话框、拖入、文件栏、最近使用、会话恢复各打开一次 TXT、源码文件和 PDF。(T81)
- [ ] F09 的 BOM、CRLF、空文件副本：不修改直接保存，SHA-256 不变；真实修改后保存，BOM 和换行风格保持。(B05)
- [ ] F09 无效 UTF-8 副本不会被覆盖写坏。(B05)
- [ ] F08 副本：front matter 原样保留；数学公式、扩展指令进入源码保护，原始 HTML、注释和脚注留在可视化模式；编辑保存后没有内容被悄悄删除。(A13)
- [ ] 11 MiB 的 `large-source-11MiB.md`：进入源码保护，能编辑并保存。超过 20 MiB 的文件拒绝打开，提示说明文件未被截断或修改。(A13)
- [ ] 保存进行中继续输入：保存完成后文档仍显示未保存。保存失败或取消时关闭标签：标签不关，内容还在。(B01)
- [ ] 带本地图片的 F04 副本“另存为…”到新文件夹：图片复制到新位置的 `assets/`，相对路径正确，新文档可独立打开，原文档不变。(A08)
- [ ] 对只读文件、已被删除的文件、同名目标各保存一次，并取消一次存储面板：原文件不损坏，不显示“已保存”，提示里有可做的操作。(A15)
- [ ] 设置 › 工作区打开自动保存：连续中文输入不被打断；外部程序改过文件后不自动覆盖；新建文档仍需手动保存；两个窗口的设置同步。(T39)
- [ ] 打开“恢复上次打开的文档”后退出重开：主窗口的标签恢复；从 Finder 冷启动打开的文件优先显示；其中一个文件已不存在时有提示。(T41)
- [ ] 连续保存同一文档 6 次，`ls -a` 确认旁边只有 1 个 `.mino-backup-<名称>-<哈希>.bak`；保存中途强制退出后文档完整。(T101)
- [ ] 从 Finder 打开 20 万字符以上的真实文档：开头很快出现，余下内容加载时可以滚动；`⌘⇧R` 进入编辑时有提示且阅读位置不丢；进入编辑后不改内容保存，文件逐字节不变。20 万字符以下的文档行为照旧。(T77)
- [ ] 状态栏字数与实际相符，选中一段时显示选区字数。(T41)

## 5. 性能测量

**实机指标。** 用 `scripts/performance-session.mjs` 记录。它把会话绑定到当前 release 主程序和规模样本的哈希，应用或样本变了就拒绝继续；每条记录必须写测量方法；报告按最近秩给出 p50 和 p95，样本数不够时显示 PENDING。脚本不判定是否达标。

```sh
./build.sh
node scripts/generate-scale-fixtures.mjs dist-package/performance-fixtures
node scripts/performance-session.mjs init <会话.json> '<机器与系统>'
node scripts/performance-session.mjs record <会话.json> <指标> <数值> '<测量方法>' ['备注']
node scripts/performance-session.mjs report <会话.json>
```

会话文件放在仓库之外。不要在测量期间运行 `./install.sh` 或 `./clean.sh`，它们会删掉被绑定的包和样本。

| 指标 | 含义 | 最少样本 | 建议目标 |
| --- | --- | --- | --- |
| `startup-ms` | 启动到可输入 | 20 | p95 ≤ 2 秒 |
| `idle-rss-mib` | 启动 60 秒后应用与其专属 WebView 进程的常驻内存合计 | 1 | ≤ 200 MiB |
| `input-ms` | 100 KiB 文档里一次输入到下一次绘制 | 20 | p95 ≤ 50 ms |
| `open-1mib-ms` | 打开 1 MiB / 1 万行文档到编辑器就绪 | 20 | p95 ≤ 2 秒 |
| `directory-first-screen-ms` | 1 万条目目录的首批条目可操作 | 1 | ≤ 1 秒 |
| `html-20-images-ms` | 20 张共约 20 MiB 图片的 HTML 导出准备 | 1 | ≤ 5 秒 |
| `html-peak-rss-mib` | 上一项的内存峰值 | 1 | 只记录 |

“建议目标”是[技术设计](02-技术设计.md)里的建议值，从未依据实测冻结；首次实测后在那里定下正式门槛。已经定下并由构建或清单检查的门槛只有：

- `Mino.app` 不超过 80 MiB（T69）；随包字体不超过 `FONT_BUDGET_BYTES`，入口包不超过 `ENTRY_BUDGET_BYTES`，两者在 `vite.config.ts`，超出时构建失败。
- 保存时主线程任务不超过 50 ms（§4.13 第一项）。

**测量规则**

- 记录硬件、系统、构建模式、应用和锁文件版本、样本哈希、次数、计时的起止点、系统缓存条件。清不了缓存时不称为严格冷启动。
- 内存要包含属于应用的 WebView 进程，不能只报 Rust 主进程。
- 不拿一次最好的结果代表 p95，不换更小的样本，不用切到源码模式的数值代替可视化的数值。
- 没达到目标就记为未通过，继续优化或提出取舍，不删掉这项指标。
- 与某个旧构建比较启动时间时，两边各测 5 次。(T98)

**同口径对比。** `node scripts/perf-baseline.mjs out.json`（先 `npm run build`）在 Node 里测解析、查找等的耗时和各包体积。它只用于同一台机器上改动前后的比较，不代表应用里的实际耗时。

## 6. 发布步骤

1. **定版本号。** 这五个文件里的版本必须相同：`package.json`、`package-lock.json`、`src-tauri/tauri.conf.json`、`src-tauri/Cargo.toml`、`src-tauri/Cargo.lock`。构建脚本从不修改版本；`build.sh` 以 `--locked` 调用 Cargo，`Cargo.lock` 对不上时停止而不是改它。
2. **写发布日志。** 在 [CHANGELOG](../CHANGELOG.md) 顶部加这一版，只写使用者看得见的变化和已知限制；`CHANGELOG.en.md` 同步。[README](../README.md) 与 `README.en.md` 里的“当前版本”和限制一并更新。
3. **跑 §2 的全部自动化检查。**
4. **构建。** `./build.sh` 产出 `src-tauri/target/release/bundle/macos/Mino.app`、`dist-package/Mino-<版本>-macos-arm64-unsigned.zip` 和 `dist-package/manifest.json`（版本、架构、最低系统声明、`.app` 与 ZIP 的 SHA-256、两个锁文件的 SHA-256、包体积）。
5. **验证。** `node scripts/package-manifest.mjs verify` 通过；按 §4 做实机验收，至少覆盖这一版改动影响到的项；结果按 §7 记录，状态更新到 [开发进度](04-开发进度.md)。有阻断发布的问题时不发布。
6. **许可。** 依赖或随包字体有变化时，重新生成并核对 `doc/licenses/` 下的许可清单（`python3 scripts/generate-rust-license-inventory.py`、`python3 scripts/generate-license-text-bundle.py --write` 再 `--verify`），并更新 `doc/licenses/bundled-font-licenses.tsv`。
7. **提交并打标签。** 提交后打 `v<版本>` 标签（现有 `v1.0.0`），推送分支和标签。

**目前没有做、不能声称的事**

- 包以 `--no-sign` 构建：没有 Developer ID 签名，没有公证，没有经过 Gatekeeper 和新机器安装的验证。没有可下载的安装包，使用者从源码构建。
- 只支持 Apple Silicon。包声明最低 macOS 12.0，但只在 macOS 27 上构建和使用过；导出 PDF 在 macOS 13.3 以下未验证。
- 项目自身的许可尚未确定；第三方许可原文仍有缺口（见 [许可原文审查](licenses/license-text-audit.md)）。公开分发之前要先解决这两项。
- 重新构建后 macOS 可能再次询问钥匙串授权。
